# Strata

A metadata-driven, multi-tenant application substrate, built around a pure Rust domain kernel,
with a Lean 4 model of that kernel, a deterministic simulator that runs the real kernel, and a
blog, **Fieldnotes**, that exists only as tenant metadata on top of it.

The kernel defines what the system means. Everything else interprets, executes, persists,
presents, proves or simulates that meaning.

## Status

The platform's intended design is the specification, `specifications/spec.jsonc`
(739 requirements, 129 model claims, milestones 1 to 12). It describes a larger system than this
repository builds: one database per tenant on PostgreSQL, a separate identity service, a gateway,
an agent plane and a cloud profile. The prototype here implements milestone 1. The gate holds the
code to the milestones listed in `concordance.toml` (`[gate] started_milestones`, currently 1),
which is 37 of the 739 requirements. The rest are planned and are not checked against the code.

The documents in `docs/` describe the prototype as it is. Where they and the specification
differ, the specification states the target. See `specifications/README.md` for what a passing
gate does and does not establish.

## Start it

Needs Rust 1.96, Node 24 and, for the proofs only, Lean 4.36 (via `elan`). No Docker, no
database server, no network once dependencies are installed.

```sh
npm install            # once
npm run dev            # or: nu scripts/dev.nu
```

That one command builds and starts the backend, the BFF and Vite, creates the SQLite database
at `var/strata.db`, installs the tenants on first start, and stops everything on Ctrl+C.

| What | Where |
|---|---|
| Fieldnotes, with hot reload | http://127.0.0.1:5173/ |
| Writing desk | http://127.0.0.1:5173/desk |
| Impact Lab | http://127.0.0.1:5173/lab |
| The second tenant, Tidewater Review | http://tidewater.localhost:5173/ |
| BFF serving the built frontend | http://127.0.0.1:4100/ (after `npm run build`) |
| Backend | 127.0.0.1:4101, loopback only, refuses anything without the service token |

Development logins (defined in `tenants/fieldnotes/accounts.dev.json`, installed only when
`STRATA_DEV=1`, never part of the tenant's data):

|---|---|---|
| `admin` | `strata-dev-admin` | owner: settings, schema, Impact Lab |
| `ines` | `strata-dev-ines` | editor |
| `tomasz` | `strata-dev-tomasz` | author |

`node scripts/dev.mjs --fresh` deletes the development database first.
`node scripts/dev.mjs --no-vite` serves the built frontend from the BFF, as a deployment would.

## Check it

```sh
cargo test --workspace     # kernel, substrate, storage, simulation, verification, backend, BFF
npm run test:web           # the frontend kernel, as plain functions
npm run check              # type-check the JavaScript through its JSDoc
npm run build && npm run e2e   # real browser: 26 tests on two stacks with their own ports
cd lean && lake build && lake env lean Audit.lean   # the proofs and the axioms they use
npm run spec               # the specification gate: the tests above except e2e, then Exegra and Concordance
```

After changing the specification, regenerate the model crate and the web modules (the gate fails while either is out of date):

```sh
npm run generate
```

This writes a placeholder `crates/model/src/lib.rs` if it is missing, then runs `specc generate` for `crates/model` and `specc web` for `web/src/generated`.

`specc deploy`, `specc e2e` and `specc scenarios` write the deployment descriptors, Playwright tests and
scenario tests from the same specification; `crates/spec-compiler` documents each. `docs/runtime.md`
states what generated code may rely on.

On a shared machine, cap the Rust build and tests: `CARGO_BUILD_JOBS=2 RUST_TEST_THREADS=2`.
`npm run spec` needs the Exegra checkout at `../exegra` (or `EXEGRA_HOME`) and `concordance` on
the PATH. Its details are in `specifications/README.md`.

## Run it in containers

Strata also runs as two Alpine containers under podman: `runtime` (the backend) and `gateway` (the BFF
with the built web bundle). `deploy/compose.yaml`, `deploy/kubernetes` and `deploy/monitoring` are
generated by `specc deploy` from the specification's components and relationships, plus
`specifications/deploy.jsonc` for what the specification does not say (ports, environment, health
paths, the database volume). `deploy/Containerfile` is hand-written, one build target per unit.
`npm run generate` rewrites the generated files and `npm run spec` fails when they are stale.

```sh
npm run containers:build            # podman compose build
npm run containers:up               # starts the stack with a fresh service token; waits until it answers
npm run containers:down             # stops it; add -- --volumes to delete the database
npm run e2e:containers              # fresh stack, then the site tests against it (STRATA_E2E_BASE_URL)
```

The gateway is the only published port (127.0.0.1:4100, or `STRATA_PORT`). The backend listens on loopback
only, so the gateway joins its network namespace instead of reaching it over a network. The database is
the named volume `strata-data`. The development logins are on unless `STRATA_DEV=0`. Against the
containers the log test reads `podman logs`, the backend-is-not-reachable test checks that nothing
answers on 127.0.0.1:4101, and the Lean test skips itself because the image has no Lean. The
hot-reload test is not part of the container run.

## What is where

```
crates/kernel           pure transition engine: no I/O, no clock, no randomness
crates/substrate        pure interpreters: bundles, expression syntax, views, Markdown, themes
crates/storage-api      the persistence contract, a memory adapter, the conformance suite
crates/storage-sqlite   every line of SQL in the project
crates/protocol         wire types: internal API, WebSocket protocol v1, log lines
crates/backend          sessions, load -> kernel -> commit, outbox, subscriptions, Lab runs
crates/bff              the browser's only entry point
crates/simulation       discrete-event simulator over the real kernel; branching; replay
crates/verification     invariants, proof obligations, Lean orchestration, correspondence
crates/runtime          the hand-written runtime generated code runs on: machine host, outbox, timers, routes
crates/spec-expr        the specification's expression language, translated to Rust and JavaScript
crates/spec-compiler    specc: compiles the specification into crates/model, deployment files and tests
crates/model            GENERATED by specc from specifications/spec.jsonc; never edit, regenerate
lean/                   the abstract model, the proofs, the executable model
web/src/kernel          the frontend kernel: update(state, message) and view(state)
web/src/worker          the Web Worker driver: every fetch and the WebSocket
web/src/views           view model to elements
web/src/styles          tokens, base, layout, components, in cascade layers
tenants/                Fieldnotes and Tidewater as data; the publication template
tests/e2e               Playwright
specifications/         the platform specification (spec.jsonc) and how to read it
scripts/                dev loop, container stack (containers.mjs), spec gate (spec-gate.mjs)
deploy/                 Containerfile; compose, Kubernetes and alert rules GENERATED by specc deploy
docs/                   architecture, invariants, decisions, storage, protocol, development, verification
```
